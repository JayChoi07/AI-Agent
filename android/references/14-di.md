# 14 의존성 주입

> 적용: 그린필드 Android(Kotlin·Compose·Navigation 3 1.1.7·Hilt·멀티모듈). 출처 번호(S..)는 90-sources.md.

DI 프레임워크는 Hilt로 고정한다. Anvil은 스스로 deprecated를 선언했고 대체 라이브러리를 지목하지 않으며 [S103](https://raw.githubusercontent.com/square/anvil/main/README.md), Metro는 "Kotlin compiler plugins are not a stable API"라는 경고를 문서 첫머리에 달고 있다 [S104](https://zacsweers.github.io/metro/latest/). Anvil을 빌드 속도 이유로 택한 사례 [S109](https://traderepublic.substack.com/p/state-of-android-at-tr-2024-edition)는 2024년 결정이라 그린필드 기본값으로 삼지 않는다.

## 스코프 결정 매트릭스

| 판단 기준 | 선택지 A | 선택지 B | 기본값 |
|---|---|---|---|
| 앱 전체가 인스턴스 하나를 공유해야 하나(DB·Retrofit·인메모리 캐시·DataStore) | `@Singleton` + `SingletonComponent` | 무스코프 | 예면 A |
| 한 화면의 ViewModel 그래프 안에서만 상태를 나눠 쓰나 | `@ViewModelScoped` + `ViewModelComponent` | 무스코프 | 예면 A |
| 상태가 없고 매번 새로 만들어도 되나(매퍼·UseCase·`@Binds` 대상 대부분) | 무스코프 | `@Singleton` | 무스코프 |
| 스코프를 정하기 애매한가 | 좁은 쪽 | 넓은 쪽 | 좁은 쪽으로 시작해 필요할 때 넓힌다 |

스코프는 공짜가 아니다. 바인딩에 스코프를 주면 컴포넌트가 사라질 때까지 메모리에 남는다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 컨테이너 스코프는 필요할 때만 지정하라는 것이 공식 권고이기도 하다 [S02](https://developer.android.com/topic/architecture/recommendations).

## Hilt 모듈 위치

| 대상 | 모듈 두는 곳 | 컴포넌트 |
|---|---|---|
| Repository 인터페이스 → 구현 바인딩(둘 다 `..data..`) | 그 Repository를 소유한 모듈의 `di/`. feature 전용이면 `:feature:<name>` 의 `di/`, 여러 feature가 쓰면 `:core:data` 의 `di/` | `SingletonComponent` |
| Retrofit·Room·DataStore 인스턴스 | `:core:network`·`:core:database`·`:core:datastore` 의 `di/` | `SingletonComponent` |
| 디스패처 qualifier 제공 | `:core:common` 의 `di/` | `SingletonComponent` |
| 한 화면 그래프에만 필요한 바인딩 | `:feature:<name>` 의 `di/` | `ViewModelComponent` |

### R-14-01 ViewModel은 `@HiltViewModel`과 `@Inject constructor`로 정의한다
- 규칙: ViewModel 클래스에 `@HiltViewModel`을 붙이고 의존은 전부 생성자 파라미터로 받는다. Composable에서는 `hiltViewModel()`로 얻고, ViewModel을 직접 `new` 하거나 커스텀 `ViewModelProvider.Factory`를 손으로 만들지 않는다.
- 근거: ViewModel은 `@HiltViewModel` + `@Inject constructor`로 정의하고 Compose에서는 `hiltViewModel()`로 가져온다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 생성자 주입 기반 DI는 공식 강한 권고다 [S02](https://developer.android.com/topic/architecture/recommendations).
- 예시:
  ```kotlin
  // Good
  @HiltViewModel
  class HomeViewModel @Inject constructor(
      private val repository: UserRepository,
      savedStateHandle: SavedStateHandle,
  ) : ViewModel()
  // Bad
  class HomeViewModel : ViewModel() {
      private val repository = DefaultUserRepository()
  }
  ```
- 체크: `ViewModel`을 상속한 클래스에 `@HiltViewModel`이 있는가. 생성자에 `@Inject`가 있는가. 본문에서 의존을 직접 생성하는 줄이 있는가.

### R-14-02 필드 주입을 쓰지 않는다(Hilt 진입점만 예외)
- 규칙: 우리가 생성자를 정하는 클래스(ViewModel·Repository·UseCase·DataSource·그 밖의 일반 클래스)는 모든 의존을 생성자 파라미터로 받는다. 필드 주입(`@Inject lateinit var`)은 Hilt가 생성자를 잡을 수 없는 프레임워크 진입점, 즉 `@AndroidEntryPoint`나 `@HiltAndroidApp`이 붙은 Activity·Application·Service·BroadcastReceiver에서만 쓴다. 그 필드도 private으로 선언하지 않는다.
- 근거: 생성자 주입 기반 DI가 공식 강한 권고다 [S02](https://developer.android.com/topic/architecture/recommendations). 다만 Android가 인스턴스를 직접 만드는 클래스는 생성자 주입이 불가능해 Hilt 문서가 Activity에 `@Inject lateinit var`를 쓰는 예를 그대로 싣고, 같은 문서가 "Fields injected by Hilt cannot be private"라고 못 박는다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 그래서 필드 주입은 캡슐화를 깨는 대신 프레임워크 제약을 푸는 용도로만 남기고, 공개 표면 최소화 원칙 [S03](https://developer.android.com/topic/modularization)에 따라 그 밖에서는 금지한다.
- 예시:
  ```kotlin
  // Good — 생성자를 우리가 정하는 클래스
  class SyncScheduler @Inject constructor(private val workManager: WorkManager)
  // Good — Hilt가 생성자를 잡을 수 없는 진입점
  @AndroidEntryPoint
  class MainActivity : ComponentActivity() {
      @Inject lateinit var analytics: Analytics
  }
  // Bad — 생성자가 있는데 필드로 받음
  @HiltViewModel
  class HomeViewModel @Inject constructor() : ViewModel() {
      @Inject lateinit var repository: UserRepository
  }
  ```
- 체크: `@Inject`가 붙은 프로퍼티가 `@AndroidEntryPoint`·`@HiltAndroidApp` 클래스 밖에 있는가. 진입점의 주입 필드가 private으로 선언돼 있는가.

### R-14-03 Hilt 진입점은 Application 하나와 루트 Activity 하나로 둔다
- 규칙: `Application` 클래스에 `@HiltAndroidApp`을 붙인다. Compose 앱은 `ComponentActivity`를 상속한 루트 Activity 하나에만 `@AndroidEntryPoint`를 붙이고 화면은 그 안에서 Composable로 전환한다.
- 근거: Hilt를 쓰는 앱은 `@HiltAndroidApp`이 붙은 Application 클래스를 반드시 가져야 하고, 주입 대상 Android 클래스에는 `@AndroidEntryPoint`가 필요하며 Activity는 `ComponentActivity` 상속만 지원한다. Compose 앱은 루트 `ComponentActivity` 하나를 단일 DI 진입점으로 쓴다 [S05](https://developer.android.com/training/dependency-injection/hilt-android).
- 예시:
  ```kotlin
  // Good
  @HiltAndroidApp class App : Application()
  @AndroidEntryPoint class MainActivity : ComponentActivity()
  // Bad — 화면마다 Activity를 만들고 전부 진입점으로 만듦
  @AndroidEntryPoint class LoginActivity : ComponentActivity()
  ```
- 체크: `@AndroidEntryPoint`가 붙은 Activity가 둘 이상인가. Application에 `@HiltAndroidApp`이 있는가.

### R-14-04 Hilt 모듈은 `@Module`과 `@InstallIn`을 함께 붙이고 `di/` 패키지에 둔다
- 규칙: 모든 Hilt 모듈은 `@Module`과 `@InstallIn(<Component>::class)`를 같이 선언한다. 모듈 파일은 그 바인딩을 소유한 Gradle 모듈의 `di/` 패키지에 두고, 다른 모듈의 내부 타입을 대신 바인딩하지 않는다. feature 전용 Repository의 `@Binds` 모듈은 그 feature의 `di/`에 둔다.
- 근거: 모듈에는 `@Module`과 `@InstallIn`을 반드시 함께 붙인다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 데이터 소스를 은닉하고 repository만 노출하는 모듈 경계를 지키려면 바인딩도 그 모듈 안에 있어야 한다 [S04](https://developer.android.com/topic/modularization/patterns).
- 예시:
  ```kotlin
  // Good — :core:data 의 di/DataModule.kt
  @Module
  @InstallIn(SingletonComponent::class)
  internal interface DataModule
  // Bad — :app이 :core:data의 internal 구현을 바인딩
  ```
- 체크: `@Module`만 있고 `@InstallIn`이 없는 클래스가 있는가. 모듈 파일 경로가 `di/`인가.

### R-14-05 인터페이스 바인딩은 `@Binds`, 외부 타입은 `@Provides`로 제공한다
- 규칙: 우리가 소유한 인터페이스와 그 구현을 잇는 것은 `@Binds` 추상 함수로 한다. 모듈은 `abstract class`가 아니라 `interface`로 선언하고 함수에 `abstract` 키워드를 붙이지 않는다(구현이 없는 `abstract class`는 detekt `AbstractClassCanBeInterface`가 잡는다). 생성자를 우리가 못 건드리는 타입(Retrofit, Room DB, OkHttp 등)이나 빌더가 필요한 타입만 `@Provides`로 만든다. `@Provides`가 섞이면 `companion object`에 둔다.
- 근거: 인터페이스 바인딩은 `@Binds`, 소유하지 않은 타입이나 빌더가 필요한 타입은 `@Provides`를 쓴다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 데이터 계층 컴포넌트를 인터페이스로 정의하고 구현을 바인딩하는 구성과 맞는다 [S54](https://raw.githubusercontent.com/android/nowinandroid/main/README.md).
- 예시:
  ```kotlin
  // Good — 인터페이스와 구현 모두 ..data.. 에서 import 한다(11-architecture-layers.md R-11-02)
  @Module @InstallIn(SingletonComponent::class)
  internal interface DataModule {
      @Binds fun bindUserRepository(impl: DefaultUserRepository): UserRepository

      companion object {
          @Provides @Singleton
          fun provideDatabase(@ApplicationContext context: Context): AppDatabase =
              Room.databaseBuilder(...).build()
      }
  }
  // Bad — 직접 만들 수 있는 타입을 @Provides로
  @Provides fun provideUserRepository(remote: UserRemoteDataSource): UserRepository = DefaultUserRepository(remote)
  ```
- 체크: `@Provides`로 제공한 타입 중 우리 코드에서 `@Inject constructor`를 붙일 수 있는 것이 있는가. `@Binds`만 있는 모듈이 `abstract class`로 남아 있는가.

### R-14-06 스코프는 필요한 최소 컴포넌트에만 지정한다
- 규칙: 위 결정 매트릭스에 따라 스코프를 고른다. 상태 없는 객체에는 스코프를 주지 않는다. `@Singleton`은 앱 전체가 인스턴스를 공유해야 하는 이유가 있을 때만 쓴다.
- 근거: 바인딩에 스코프를 주는 것은 비용이 있고 컴포넌트가 사라질 때까지 메모리에 남는다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 필요할 때만 컨테이너에 스코프를 지정하라는 권고 [S02](https://developer.android.com/topic/architecture/recommendations).
- 예시:
  ```kotlin
  // Good — 상태가 없으니 무스코프
  class UserMapper @Inject constructor()
  // Good — 연결 풀을 공유해야 하니 앱 전역
  @Singleton @Provides fun provideOkHttp(): OkHttpClient = OkHttpClient()
  // Bad
  @Singleton class UserMapper @Inject constructor()
  ```
- 체크: 새로 붙인 `@Singleton`마다 공유해야 하는 상태나 자원이 실제로 있는가.

### R-14-07 같은 타입을 여러 개 제공할 때만 `@Qualifier`를 쓰고, 도입하면 모든 경로에 붙인다
- 규칙: 한 타입에 바인딩이 둘 이상일 때 `@Qualifier` 애노테이션을 정의해 구분한다. 어떤 타입에 qualifier를 도입했으면 그 타입을 제공하는 모든 경로와 주입 지점에 빠짐없이 붙인다.
- 근거: 동일 타입 다중 바인딩은 `@Qualifier`로 구분하고, 한 타입에 qualifier를 도입하면 모든 제공 경로에 붙여야 한다 [S05](https://developer.android.com/training/dependency-injection/hilt-android).
- 예시:
  ```kotlin
  // Good
  @Qualifier @Retention(AnnotationRetention.RUNTIME) annotation class AuthClient
  @AuthClient @Provides fun provideAuthClient(): OkHttpClient = ...
  // Bad — 같은 타입 두 개를 이름으로만 구분
  @Provides fun provideAuthOkHttp(): OkHttpClient = ...
  @Provides fun providePlainOkHttp(): OkHttpClient = ...
  ```
- 체크: 같은 타입을 제공하는 `@Provides`·`@Binds`가 둘 이상인데 qualifier가 없는 것이 있는가.

### R-14-08 `CoroutineDispatcher`는 qualifier로 주입한다
- 규칙: `Dispatchers.IO`·`Dispatchers.Default`를 클래스 안에 직접 쓰지 않는다. `@IoDispatcher`, `@DefaultDispatcher` qualifier를 `:core:common` 의 `di/`에 정의하고 생성자로 주입해 테스트에서 교체할 수 있게 한다.
- 근거: 동일 타입 다중 바인딩을 qualifier로 구분하라는 규칙의 적용이다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). repository·데이터 소스는 스스로 적절한 디스패처로 옮겨 main-safe해야 하고 [S06](https://developer.android.com/topic/architecture/data-layer), use case도 장시간 작업에서 디스패처를 옮기며 디스패처를 의존으로 받는다 [S07](https://developer.android.com/topic/architecture/domain-layer).
- 예시:
  ```kotlin
  // Good
  @Qualifier @Retention(AnnotationRetention.RUNTIME) annotation class IoDispatcher
  class DefaultUserRepository @Inject constructor(
      @IoDispatcher private val ioDispatcher: CoroutineDispatcher,
  )
  // Bad
  suspend fun load() = withContext(Dispatchers.IO) { ... }
  ```
- 체크: 프로덕션 코드에 `Dispatchers.IO`·`Dispatchers.Default` 리터럴이 있는가(디스패처 제공 모듈은 예외).

### R-14-09 Hilt가 지원하지 않는 클래스는 `@EntryPoint`로만 접근한다
- 규칙: `ContentProvider`처럼 Hilt가 직접 주입하지 못하는 클래스에서 의존이 필요하면 `@EntryPoint` 인터페이스를 정의하고 `EntryPointAccessors`로 얻는다. 싱글턴 객체나 정적 필드에 의존을 담아 우회하지 않는다.
- 근거: Hilt 미지원 클래스는 `@EntryPoint` + `EntryPointAccessors`로 접근한다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). 앱 컴포넌트에 데이터를 저장하지 말라는 원칙과 같은 방향이다 [S01](https://developer.android.com/topic/architecture).
- 예시:
  ```kotlin
  // Good
  @EntryPoint
  @InstallIn(SingletonComponent::class)
  interface AnalyticsEntryPoint { fun analytics(): Analytics }
  // Bad
  object ServiceLocator { lateinit var analytics: Analytics }
  ```
- 체크: 의존을 담아 두는 전역 `object`나 정적 필드가 있는가.

### R-14-10 테스트는 생성자로 fake를 넣고, 그래프 교체는 계측 테스트에만 쓴다
- 규칙: 로컬 단위 테스트는 Hilt를 켜지 않고 생성자에 fake를 직접 넘겨 대상 클래스를 만든다. Hilt 그래프 자체를 바꿔야 하는 계측·Robolectric 테스트에서만 테스트 전용 모듈로 프로덕션 모듈을 대체한다(`@TestInstallIn`).
- 근거: 생성자 주입 기반 DI와 mock보다 fake 선호가 공식 권고다 [S02](https://developer.android.com/topic/architecture/recommendations). 테스트 더블은 실제 구현을 대체하는 fake를 우선한다 [S31](https://developer.android.com/training/testing/fundamentals/test-doubles). 테스트 전용 모듈에도 `@Module`·`@InstallIn` 규칙이 그대로 적용된다 [S05](https://developer.android.com/training/dependency-injection/hilt-android). `@TestInstallIn`은 Hilt 테스트 API 이름이며 이 팩이 확인한 출처(S05)의 범위는 `@Module`·`@InstallIn`까지다.
- 예시:
  ```kotlin
  // Good — 로컬 단위 테스트
  val viewModel = HomeViewModel(FakeUserRepository(), SavedStateHandle())
  // Bad — 단위 테스트에서 Hilt 컴포넌트를 띄움
  @HiltAndroidTest class HomeViewModelTest
  ```
- 체크: 로컬 단위 테스트가 Hilt 애노테이션을 쓰는가. fake가 프로덕션 인터페이스를 구현하는가.
