원인 계층에서 고친다. 증상이 UI에 보여도 원인이 data 계층이면 data에서 고치고, UI에서 덮지 않는다 (R-11-01). 이번 수정과 무관한 개선은 넣지 않는다 (R-00-05).

**수정이 새 결함을 만들지 않게 한다.** 사례(2026-10-20): 전역 푸시 전환의 끊김을 고친 변경이 `NavDisplay` metadata로 전환을 따로 지정한 모달에도 걸려 대각선으로 들어왔다. 횡단 변경을 고쳤다면 (1) 그 메커니즘의 **호출·등록 지점과 예외 설정**(예: 전환 metadata를 따로 지정한 엔트리, 테마·잠금의 예외)을 검색해 영향 경로를 **목록으로 만들고**(검색어와 찾은 개수를 적는다) (2) 경로마다 기대 동작(공통 처리를 받는가·건너뛰는가·다르게 받는가)을 정하고 (3) 경로마다 맞는 방법으로 확인한다 — 화면 모양은 실기기·골든·느린 배율 캡처, 잠금·수명주기 같은 동작은 시험·로그로. 목록에 없거나 확인하지 못한 경로는 "확인 안 함"으로 보고한다. 전환의 사례는 R-28-01(직접 그린 푸시 움직임).

**시험이 못 보는 부류는 기기에서 본다.** 사례(2026-10-20): ① `stickyHeader` 배너·지도가 상태 바 뒤로 들어가 윗부분이 잘렸고(R-17-16) ② 긴 바텀시트가 열린 뒤 2초 넘게 윗면이 올라갔다(R-28-22). 둘 다 만든 지 하루 뒤 사용자가 발견했다 — 스크린샷 테스트는 스크롤하지 않은 정지 화면을 찍고 시트는 별도 창이라 내용만 찍기 때문이다. 인셋에 걸리는 고정 요소, 스크롤하면 위치가 바뀌는 요소, 별도 창 오버레이, 열리는 도중의 움직임은 골든·단위 시험에 보이지 않는다. 이런 UI를 만들거나 고칠 때는 (1) 시험이 무엇을 못 보는지 먼저 적고 (2) 기기에서 **스크롤한 상태**와 **열린 지 2초 뒤 상태**를 캡처·녹화해 위치·높이 값을 잰다. 팩 규칙의 예시를 그대로 따랐는데 결함이 났다면(이 사례의 R-18-08은 `contentPadding` 예시가 `stickyHeader`와 만나 문제였다) 코드만 고치지 말고 규칙의 예외를 고친다.

**원인이 팩의 공백·잘못으로 판명되면 팩도 고친다.** 근본 원인이 선호가 아니라 확실한 잘못이고(재현·측정·소스로 확인) 같은 코드 형태가 다른 프로젝트에서도 같은 결과를 낼 것이면, README F절 절차로 규칙(또는 기존 규칙의 예외)·조사 노트·출처를 갱신하고 `check-pack.sh`를 통과시킨다. 원인이 가설인 단계는 규칙으로 올리지 않고 조사 노트에 "미확인"으로 남긴다(README F.1).

## 구현 순서
1. 재현 테스트 작성 — 결정 1의 위치
   → 검증: 수정 전에 이 테스트가 실패한다(실패 메시지를 기록) (R-30-01, R-30-06)
2. 원인 지점 최소 수정
   → 검증: 변경 파일이 원인 계층에 한정, 새 추상화 없음 (R-11-01, R-00-05)
3. 실패 경로 정리 (해당할 때)
   → 검증: 예외는 데이터 계층 경계에서 도메인 타입으로, `CancellationException`은 다시 던짐, 로그에 개인정보 없음 (R-23-05, R-22-10, R-23-09)
4. 재현 테스트 통과 확인
   → 검증: 1에서 실패하던 테스트가 통과 (R-30-01)
5. 인접 테스트 실행 — 결정 4의 범위
   → 검증: 기존 ViewModel 테스트·스크린샷 테스트 통과, 스크린샷 기준 이미지를 재기록하지 않음 (R-30-01, R-30-03, R-30-04) 횡단 변경이면 위 영향 경로 목록의 각 경로를 그 경로에 맞는 방법으로 확인했다
6. ktlint·detekt·단위 테스트 실행
   → 검증: 0 이슈 (R-31-01)
7. 원인 분류 — 근본 원인이 팩의 공백·잘못인가
   → 검증: 그렇다면 위 "원인이 팩의 공백·잘못으로 판명되면" 절차로 팩을 갱신했거나, 가설이라 조사 노트에 "미확인"으로 남겼다
