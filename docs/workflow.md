# 당일 운영 플레이북

> 전제: 하루짜리 해커톤, 당일 출시, 블라인드 리포트 심사. 총 가용 시간을 T라 하면 아래 비율로 타임박스.

## 페이즈 배분 (예: T=8시간 기준)

| 페이즈 | 시간 | 하는 일 | 산출물 |
|--------|------|---------|--------|
| 1. 문제 정의 | ~1h | 과제 해석, 해석 갈리는 지점 기록, 성공 기준 확정, **제외 범위** 확정 | task-plan.md |
| 2. 골격 출시 | ~1h | **실행 가능한 최소 데모 아티팩트부터 확보** — 웹이면 빈 화면이라도 배포 URL, CLI/분석 과제면 end-to-end로 도는 최소 파이프라인 | 데모 아티팩트 |
| 3. 구현 | ~4h | 병렬 에이전트 분배, 기능 단위 검증 루프 | 작동 기능 |
| 4. 검증·경화 | ~1h | 교차 리뷰(생성자↔검증자 분리), 엣지 케이스, 데모 시나리오 리허설 | 검증 기록 |
| 5. 리포트 | ~1h | WORKLOG → templates/report.md 작성 | 제출 리포트 |

## 페이즈별 규칙

### 1. 문제 정의
- 코드 먼저 치지 않는다. "무엇이 성공인가"를 문장으로 확정하고 시작.
- 심사 포인트가 "구조화된 사고"이므로, **기각한 대안도 WORKLOG에 남긴다.**

### 2. 골격 출시 (가장 중요한 역발상)
- 데모 경로를 마지막에 뚫으면 마지막에 터진다. **과제 유형을 확인한 뒤**, 웹이면 배포부터 뚫고
  이후 push→자동배포만 반복. 웹이 아니면 "심사자가 결과를 보는 경로"(실행 스크립트/노트북)를 먼저 확보.

### 3. 구현
- 기능마다: task-plan 한 줄 → 구현 → 검증 기준 통과 → WORKLOG 기록 → 커밋.
- 30분 이상 막히면 스코프를 자른다. 해커톤에서 매몰비용은 즉시 손절.
- 독립 기능 2개 이상이면 에이전트 병렬 분배.

### 4. 검증·경화
- 구현한 에이전트가 아닌 **다른 에이전트/도구로 리뷰** (Claude 구현 ↔ Codex 리뷰 교차).
- 데모 시나리오를 처음부터 끝까지 2회 통주(通走). 데모에 안 쓰는 결함은 고치지 않는다.

### 5. 리포트
- templates/report.md 구조대로. 3번 섹션(AI Steering 방식)에 시간의 절반을 쓴다.
- "AI가 틀렸고 검증 루프가 잡았다"는 사례 1~2개는 반드시 포함 — 공개 토론에서 가장 강한 카드.

## 막혔을 때 원칙

- 같은 접근 3회 실패 → 접근 자체를 바꾼다 (에이전트에게 "다른 방법 3개 제시"부터).
- 시간 절반 지났는데 데모로 보여줄 게 없다 → 스코프를 절반으로.
- 뭘 자를지 애매하면: **데모 시나리오에 나오는가?** 안 나오면 자른다.
